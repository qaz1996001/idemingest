# idemingest — 讓重跑是安全的，而不是追求一次就成功

一個可以直接執行的小專案，用來示範一個設計決策：**當感測器資料要寫進不只一個地方、而中途連線會斷的時候，與其想辦法保證「剛好只成功一次」，不如讓每一批資料都能安全地重跑。**

```bash
uv run --with pytest pytest -q      # 15 passed
```

不需要任何外部服務。沒有 broker、沒有伺服器、不連網路。唯一的相依是 `pytest`。

程式實際怎麼跑的四個視圖——程式流程、資料流、資料狀態、使用情境——在 [docs/architecture.zh-TW.md](docs/architecture.zh-TW.md)。

---

## 問題

工業閘道會上傳一次量測的結果——同一個時間點擷取的好幾個感測器檔案。伺服器收到後要寫進兩個沒有共同交易管理器的儲存。而上傳走的是行動網路，會斷。

所以重複資料是常態。可能是閘道自己重試了，可能是有人把積壓一整天的資料補傳，也可能是某個 worker 寫完一邊就崩了。

直覺的解法是做分散式交易。比較便宜的解法是讓重複變成無害。

## 決策

**用 `(裝置編號, 內容指紋)` 去重，並且讓恢復路徑就是平常在跑的那條路徑。**

> 圖：[docs/design.zh-TW.md § 1](docs/design.zh-TW.md#1-去重鍵以及為什麼恢復不是另一條路徑)

| | 兩階段提交 | 冪等重放 |
|---|---|---|
| 需要協調器 | 要 | 不要 |
| 參與者在提交途中死掉 | 卡住，要走恢復協議 | 什麼都沒寫成，重跑就好 |
| 做錯的代價 | 懸置交易，要人工介入 | 浪費一次重跑 |
| 要維持正確的程式路徑 | 正常 + 恢復，兩條 | **一條** |

最後一列才是真正的理由。一年只跑兩次的恢復路徑，是沒有人會注意到它已經壞掉的路徑。這裡的 `replay()` 就是對 `ingest()` 跑迴圈——**恢復路徑就是每天在跑的那條**，所以它不會偷偷腐爛。

### 為什麼指紋算的是整批，不是單一檔案

逐筆上傳沒有東西可以拿來當去重的單位：每筆讀數都很小、數量龐大，而且跟下一筆長得差不多。把一次擷取綁成一個單位，才有值得計算雜湊的對象。

指紋在計算前會**先依檔名排序**，所以上傳順序不會改變指紋。這點實務上很重要，因為重試經常會改變檔案送達的順序。

### 為什麼失敗只分成兩類

```
CorruptFile    確定性失敗。重試會讀到同樣的位元組。
               → 標記失敗，只試一次。
TransientError 位元組沒問題，是當下環境忙碌。
               → 有上限地重試。
```

重試確定性失敗，是一條進料佇列死掉的典型方式：毒訊息永遠回來，把後面排隊的東西全部餓死。

> 圖：[docs/design.zh-TW.md § 2](docs/design.zh-TW.md#2-為什麼確定性失敗永遠不重試)

分類刻意只有兩個成員。**是哪個剖析器壞了、哪個 socket 逾時，那是日誌的細節，不是重試決策的輸入。**

### 執行順序就是設計

```
1. 計算批次指紋      便宜，無 I/O
2. 已經存過了嗎      → 是重複，什麼都不碰
3. 驗證              → 確定性失敗在這裡終結，不進重試迴圈
4. 原子性寫入        → 只有這一步外面包重試
```

第 1、2 步讓重放幾乎免費（測試會檢查 `attempts == 0`）。第 3 步排在第 4 步前面，確保已知的壞批次進不了重試迴圈。

## 測試證明了什麼

測試才是這個專案的主體，實作刻意寫得很小。

**冪等性**（`test_idempotency.py`）
- 同一批跑兩次，資料庫快照**位元組等價**
- 重放十次只產生一筆批次列、零筆多餘的檔案列
- 重複進料完全不做事（`attempts == 0`）
- 調換檔案順序不會改變指紋
- 兩台裝置產生位元組相同的讀數時，會被當成兩筆保留——鍵是 `(裝置, 內容)`，不是只有內容

**失敗分類**（`test_failure_classification.py`）
- 壞檔即使在重試上限設為 5 時，也**只被驗證一次**
- 暫時性失敗重試後在第 3 次成功
- 永久故障在上限處停下，並記錄原因
- **完整的恢復情境**：故障 → `FAILED`；故障排除 → 重放 → `STORED`；再重放 → `DUPLICATE`，最終狀態是一筆

**原子性**（`test_atomicity.py`）
- 以 SQLite 的 `RAISE(ABORT)` 觸發器注入失敗，所以中斷發生在**真實程式開啟的真實交易裡**，不是繞著 mock 轉
- 批次寫到一半中斷之後：**批次列 0 筆、檔案列 0 筆**
- 故障排除後，同一批資料以一次乾淨的首次進料完成
- 不變量檢查：每一筆已儲存批次宣告的 `file_count`，等於它實際的檔案列數

## 限制

寫出來是因為一個藏起邊界的示範沒有用。

- **單行程、單寫入者。** 同一批資料並行進料時，靠 `INSERT OR IGNORE` 讓後到者無害地落敗；但前置檢查與寫入之間不是原子的，所以真正並行時落敗的那一方會回報 `STORED` 而不是 `DUPLICATE`。**儲存的狀態仍然正確**，不正確的只有回報值。
- **不儲存實際酬載**，只存檔名、大小與雜湊。真實的物件儲存是這個問題比較有趣的另一半，不在這裡的範圍內。
- **對整個酬載算 SHA-256** 在這個規模沒問題，在高吞吐下是錯的；正式環境應該邊串流落地邊算雜湊，而不是把酬載整個放在記憶體裡。
- **沒有訊息代理。** MQTT／AMQP 的傳遞語意正是造成這些重複的原因，但加進來會讓測試需要基礎設施，而需要基礎設施的測試就會沒有人跑。
- **重試沒有退避。** 真實的客戶端需要指數退避加抖動；這裡省略是為了讓重試的斷言保持可預期。

## 這是從哪來的

這是我在一個工業 IoT 平台上做過的設計決策，從零重新實作一次。那裡的感測器資料要落進兩個儲存，環境沒有分散式交易可用，而上行連線並不可靠。
